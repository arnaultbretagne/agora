# ADR 0006 — Harness images are trusted, complete and hostile at runtime

- **Status:** Accepted
- **Date:** 2026-08-13

## Context

Agora supports several harnesses, personas, skills and capabilities.

Building a different image for each combination would create a support matrix. Installing tools
when a runtime starts would make execution depend on mutable network state and unaudited code.

Tool availability must also remain distinct from authorization. Code selected or generated by a
model cannot be trusted merely because its image was built by Agora.

## Decision

Each supported harness runs from a trusted immutable image pinned by digest.

Each harness definition has a stable `harness_id`. It identifies the reviewed integration used for
Session provenance and Anchor selection; it is not a process or runtime identity.

Supported harness definitions and the common tool catalogue are reviewed, versioned repository
files rather than mutable product rows. Session facts record the selected `harness_id` and resolved
artifact digests that were actually used.

Every harness image contains:

- its pinned harness and ACP adapter;
- the same complete, versioned bundle of every supported MCP server, CLI and tool executable.

Every supported MCP and tool integration is exposed to every harness through the same fixed,
reviewed registration. Capability selection never adds or removes software, descriptors or
registration.

There is no per-harness capability matrix and no image variant for a persona, skill or capability
combination. Agora installs or downloads nothing as part of Pod realization.

Adding, removing or upgrading a supported tool changes the common bundle and rebuilds and tests
every harness image.

Personas and skills are versioned files or configuration selected by Intent. Their effective
versions are recorded with the Session, but they grant no authority. Security never depends on a
hostile process being unable to find, copy or invoke an available file or executable.

Trust applies to the provenance of the image, not to the running execution. The harness process and
everything it can execute remain hostile. A runtime receives no provider secret, OneCLI control
authority, Kubernetes control authority, product database access, Save-store access or access to
another runtime.

## Why this choice

One complete bundle gives every harness the same supported tool environment and removes a
combinatorial compatibility model.

Pinned images make startup reproducible and auditable. Keeping authority outside the runtime
remains safe even when hostile code invokes any bundled executable.

The central statement of this decision is:

> Everything supported is present everywhere; presence grants no authority.

## Options considered

### 1. One image per harness and capability combination

Rejected because combinations multiply, drift and become durable compatibility claims.

### 2. Install tools at runtime

Rejected because startup becomes mutable, network-dependent and no longer attested by the image
digest.

### 3. Include only the tools a Session may use

Rejected because installed software is not an authorization boundary inside a hostile process.

### 4. Treat a trusted image as a trusted execution

Rejected because model-generated actions, prompt injection and invoked tools remain adversarial
inputs after the image has been verified.

## Consequences

- Harness images are larger and every tool change rebuilds all of them.
- Every Session runs a fully pinned harness and tool environment.
- Personas and skills can vary without creating image variants.
- Policy must assume that any bundled executable can be invoked.
- Supply-chain and compatibility tests cover the common bundle in every harness image.
